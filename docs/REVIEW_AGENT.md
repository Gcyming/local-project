## 一、角色定义

本 Agent 对 slime 项目负责三件事：

1. **审查（Review）**：主动发现用户已指出或未指出的漏洞、不足、静默失效、文档脱节、死代码；
2. **改进（Improve）**：修复问题、实现用户提出的各种需求（含"奇怪需求"），遵守项目既有约定；
3. **校验（Validate）**：每次改动后回归验证，问题修复必须"有证据"才算闭环（测试通过 / 手工复现对比）。

**铁律**：
- 改代码前先读懂，改完必须有验证证据；不凭猜测下结论。
- **资产策略（用户 2026-08-15 明确）**：当前 `config/skills/` 的 417 个技能与 slime.toml 里的 MCP 服务器**均为压测资产**——用于检验 skill/MCP 功能是否正常，可用但不是最终生产内容；**slime 构筑完成后用户将全部清空**。因此：① 不为其做保留性/迁移性投资；② 机制健壮性（空技能目录、零 MCP 服务器）必须作为验收状态测试——"清空后系统仍健康"是隐含需求；③ A-004 的 skill_search/skill_lookup 重构、A-002 的 mcp_* 沙箱策略均按机制设计，与具体压测资产无关。
- **纵观全局**：修改要看清全局耦合面（先 grep 引用面再动手），不出现"改好一个问题催生多个问题"；每次编辑后立即跑受影响模块的测试，不留隔夜债。
- **反向查验**：执行用户任务时，对照项目全局约束反查用户指令本身是否与项目铁律冲突（如"直写 agents.json"违背 promote 走 API 的约定），冲突时先指出再执行可行部分。
- **测验/编译禁用 PowerShell**：测试与编译一律走纯 Python 入口 `py qa.py`（compileall → run_tests.py → pytest，UTF-8 报告落盘 data/qa_report.json）；PowerShell 仅作零参数启动器（`py qa.py`），严禁用 PowerShell 管道/引号/重定向处理测试输出，杜绝转义与编码损坏项目文件。
- 遵守 CLAUDE.md 项目约定：promote 走 API、run_tests.py 不注入 monkeypatch 等 fixture、max_output 上限 65536、同名工具拒绝覆盖等。
- 修复优先最小改动，安全默认 fail-closed，不为修一个问题引入新风险。
- 用户"奇怪需求"是最高优先级输入，处理时先确认需求边界，再实施。

## 二、对标基准（Claude / OpenClaw / Hermes / Codex）

| 维度 | 权重 | 对标要求 | 检查手段 |
|---|---|---|---|
| 功能完整性 | ★★★ | 声明能力全部真实可用（无空目录/假就绪/占位符残留）；CLI/API/模型链路无能力不对称 | 逐链路实测 + 代码交叉核对 |
| 安全性 | ★★★ | 认证/加密/沙箱 fail-closed、SSRF/注入/路径穿越防御、密钥不落盘明文、未知输入默认拒绝 | 对抗式审查 + 测试 |
| 健壮性 | ★★★ | 崩溃可恢复、陈旧状态可自愈、并发安全、降级不静默失效 | 故障注入 + 状态复现 |
| 测试与验证 | ★★★ | 每个模块有直接测试；双入口（run_tests.py + pytest）全绿；无收集错误 | 双入口实测 |
| 代码质量 | ★★ | 无死代码/忙等/重复逻辑；错误语义一致；命名与注释对齐实际行为 | 静态扫描 + 引用追踪 |
| 性能与成本 | ★★ | token 预算自律（tools/system prompt 不无谓膨胀）；无事件循环内阻塞 I/O；无 O(N²) 热路径 | 请求构造审查 + 实测 |
| 架构 | ★★ | 分层清晰、单点编排、扩展点开放、跨路径行为一致 | 调用图梳理 |
| 用户体验 | ★★ | CLI/SSE 渲染正确、错误提示友好、命令帮助齐全 | 手工冒烟 |
| 文档对齐 | ★★ | CLAUDE.md 阶段状态/行号引用与代码一致，设计文档反映现实 | 逐文档核对 |

**验收门（Release Gate，全部满足才算"无问题"）**：
1. `py qa.py` 全绿（compileall + run_tests.py + pytest 三阶段，exit 0；PowerShell 仅作启动器）；
2. 问题登记表 P0/P1 清零，P2 有明确计划或在途；
3. 关键链路手工冒烟：server 启动 → CLI 对话（含记忆注入/工具调用）→ MCP 工具真实可调 → 本地模型懒加载/卸载 → 崩溃后重启自愈；
4. 无空目录、无假就绪、无占位符冒充实现。

## 三、每轮工作流

```
① 收集输入：用户需求 / 上轮遗留 / 新一轮扫描发现
② 定位证据：读代码 + 复现（测试/实测），写清位置与影响；grep 全局引用面再动手
③ 修复：最小改动，遵守项目约定，涉及安全的默认 fail-closed
④ 补测试：对齐 run_tests.py 发现规则（只用 tmp_path，不用 monkeypatch/capsys）
⑤ 回归验证：py qa.py（纯 Python，禁用 PowerShell 管道）+ 必要的手工冒烟
⑥ 记录：更新下方问题登记表（状态/证据/验证方式）
```

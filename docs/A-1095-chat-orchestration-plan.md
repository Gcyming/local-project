## 1. 现状取证（读代码所得，非猜测）

### 1.1 数据层：时间线已是「扁平交错数组」

`todoPanorama.ts`：

```ts
interface TimelineStep { kind: "think"|"tool"|"plan"|"todo"|"steer"; … }
appendTimelineStep(steps, ev)   // think 段自动与相邻 think 合并；tool 独立成段
```

**关键事实**：`ChatPanel.onChunk` 里 `reasoning` 与 `chunk` **已在数据层分流**——
`reasoning` → `appendTimelineStep({kind:"think"})`；`chunk` → `partialRef.current += …`（**不进时间线**）。
⇒ **正文当前根本不经过时间线**，它与思考的交错纯粹是「渲染位置」造成的（两者在同一容器里前后相邻）。

### 1.2 渲染层：两处各自成区，且工具**双份**

- `ThinkingPanel`（`ChatPanel.tsx` ~1652）：`timeline.map(step => <TimelineNode/>)` —— 时间线**已**按序渲染
  think/plan/todo/steer/**tool**，工具卡**本来就住在这里**。
- 流式正文区（~5701）：`splitStreamFade(shown)` → Markdown + 尾巴 span。
- `LiveStatusLine`（~931，挂在 5735）：主句 `status.text` + 副句 `detail` + **激励语 `cheer`**，
  容器是 `display:flex; flexWrap:wrap`。

**⚠️ image#1 的真相**：截图里「工具调用折叠块（执行命令×14…）+ 下方逐条平铺工具卡」**不是两个产地**，
而是**同一个时间线**在 `ThinkingPanel` 内渲染的两种节点（`plan` 汇总行 + 逐条 `tool` 行）。
用户说的"平铺混乱"= 时间线里 **think 段与 tool 段同权重平铺**，缺少「一组」的视觉从属。

### 1.3 激励语的折行缺陷（已确认）

`LiveStatusLine` 的 flex 行内，`status.text` / `detail` / `cheer` 三者同级。
`cheer` 是完整句子（含表情），一旦偏长就把主句挤到下一行（`flexWrap:wrap`），
观感=「状态行莫名其妙断成两行」。用户要求：**激励语换到最后一行**。

### 1.4 token 监测：两条路径**对称**，非链路缺陷

`onChunk` 里 `reasoning` 与 `chunk` **都**做 `+= len` + `recomputeStreamTokens()` + `ensureStreamTimer()`；
`buildCtxPayload` 输出 `liveReplyTokens` / `liveReasonTokens`；`liveMonitor.ts` 是单一真源，
右栏 250ms 主动 poll。⇒ **不是统计链路问题**，真因是：
① 上游推理模型在长思考期**不吐正文**（reasoning 先到、content 后到）；
② 本地口径 `≈4 字符/token`（业界唯一可行做法，协议层拿不到逐 chunk 精确 output token）。

## 2. 数据模型改造（#8 + #9 的共同地基）

### 2.1 引入「阶段组」= `TimelineGroup`

**判据（唯一出处）**：一个阶段组 = 一次「思考（可含多段）→ 其间的工具调用 → 该阶段正文」。
组的边界由**新思考段的开始**划定（`think` 段再次出现 = 上一组收尾、新组开启）。

```ts
/** 阶段组：一个"工作阶段"。渲染层按它分组，数据层仍是扁平 TimelineStep[]（向后兼容）。 */
interface TimelineGroup {
  /** 组内成员在 timeline 里的下标区间 [start, end)（**不改 timeline 本身**，只做投影） */
  from: number; to: number;
  /** 组的主思考段（组内第一个 think 的摘要；用于折叠态标题） */
  headline: string;
  /** 组内工具调用条数（折叠态 "N 步" 的数字） */
  toolCount: number;
  /** 组是否仍是"当前活跃组"（末尾、且流未结束）—— 活跃组**不自动折叠** */
  active: boolean;
}
```

**关键设计取舍：投影而非改结构。** 新增 `groupTimeline(steps): TimelineGroup[]`（纯函数，住 `todoPanorama.ts`），
**不动** `TimelineStep` 与 `appendTimelineStep`。理由：
- 现有 12 个 `todo-panorama.spec` 用例 + 持久化格式（消息里存的是扁平数组）**全部不动** → 零迁移风险；
- 分组是**纯投影**，可单独 vitest 直测（不需要渲染 DOM）；
- 将来若"组"需要持久化（如记住展开态），再加字段，届时是一次独立的小改动。

### 2.2 正文归属（#8 的数据侧）

现在正文不进时间线 ⇒ 「思考结束后统一输出」只需**渲染层延迟**，无需动数据层：

- **流式期**：正文照旧写进 `partialRef`（**必须继续写**：token 统计、断流兜底、持久化都依赖它），
  但**渲染层把 `partialRef` 的可见部分钳住**——即"思考未结束前，正文区显示为空/不显示"。
- **判定"思考是否结束"**：~~上游协议事实——`reasoning_content` 字段消失即思考结束（DeepSeek 范式）。
  本地等价判据：**收到第一个 `chunk`（正文）** = 思考已结束（因为正文跟着思考走）。
  ⇒ 引入 `contentPhaseRef: "thinking" | "content"`，首个 `chunk` 到达即切 `"content"`。~~
  > ⚠️ **以上判据已被实测推翻（2026-09-24）**：agentic 轮内事件序列是
  > `reasoning → tool-start → tool → chunk → tool-start → tool → chunk → done` ——
  > **正文与工具在一轮内反复交错**，首个 chunk 只说明"这一段写完了"，
  > **不是"思考结束"** ⇒ 该单向闩第一段正文就永久敞开，与改动前无差别。
  > 现判据：**`!loading`**（本轮全部工作收尾）＋ 常驻挂载（关闸期 `display:none`，
  > 保住 `StreamFadeText` 的渐入水位）＋ 占位文案区分「思考与工具调用进行中」/「正在思考」。
- **收尾整理**：`onDone` 时把整段正文作为**该轮的最终正文**渲染（现在本来就是这么做的，无需改）。

⚠️ **用户明确允许的例外**：「也可以在思考历程中穿插正文输出」。⇒ 实现上不做"无条件推迟"，
而是**按阶段**：某一阶段内若正文先于工具调用到达，该段正文**留在该阶段组内**（不推到末尾）；
只有当正文出现在**思考仍在进行中**时才钳住。折中判据见 §3.2。

## 3. 渲染层改造

### 3.1 阶段组渲染（#9）

`ThinkingPanel` 的 `timeline.map` 改为 `groupTimeline(timeline).map(...)`，每组渲染为：

```
┌ 组容器（.tl-group）────────────────────────────┐
│ ⌄ [组标题行]  ✔ 运行校验、修改：…\src\main\index.ts   │  ← headline（组内首个 think 摘要，去 markdown）
│                                                       │     活跃组：展开态 + 流式尾巴
│   ├ ✔ 检查 index.ts 是否已引入 AUMID                  │  ← 组内成员（think/tool/plan/todo）
│   ├ ✏ 编辑 index.ts  +3 -0                            │
│   ├ ✔ 查找所有写入类工具的 diff 标记产地               │
│   └ …                                                 │
└───────────────────────────────────────────────────────┘
```

- **活跃组（末尾未结束）**：默认**展开**，成员实时追加（工具行**实时**出现 —— 满足用户"实时显示"要求）。
- **已结束组**：默认**折叠**为一行标题（`✔ <headline>` + `N 步`），点击展开。
- 折叠/展开**沿用既有 `collapse` + `--collapse-dur` 机制**（常驻挂载 + 切 `is-open`），
  **不新增第二套动画**（项目铁律）。

**与 image#4 的对应**：image#4 的 `✔ 运行校验… → ✔ 检查… → ✏ 编辑 index.ts +3 -0 → …`
正是「组标题行 + 组内成员」两层次；本方案即该设计的直接实现。

### 3.2 正文后置（#8）

流式正文区（~5701）加一道**闸门**：

```ts
// 渲染层闸门：思考进行中 → 正文区不渲染流式正文（进度仍由 LiveStatusLine 表达）
const showStreamingBody =
  !streaming || contentPhaseRef.current === "content" || /* 该阶段已收尾 */ false;
```

- `streaming && phase==="thinking"`：正文区**不显示**流式正文（只显示思考历程 + 状态行）。
- 首个 `chunk` 到达（`phase→"content"`）：正文区**开始**渲染（此时思考通常已基本结束）。
- `onDone`：渲染完整正文（终态，与现在一致）。

⚠️ **不变量**：`partialRef` **继续累积**（token 统计/兜底/持久化依赖它）。闸门**只管显示**。
⇒ 守卫：断言"闸门关闭时 `partialRef` 仍在增长"（防有人把闸门写成不写 ref）。

> ⚠️ **本节已按实际实现更正（2026-09-24）**：上面的 `contentPhaseRef` 版闸门**从未真正生效**
> （前提错误，见 §2.2 更正框），已删除。**实际实现**（`ChatPanel.tsx`）：
> ```tsx
> const gateOpen = !loading;
> <div style={gateOpen && shown ? undefined : { display: "none" }}>
>   <StreamFadeText text={shown} />

> {(!gateOpen || !shown) && (<span>{runningTool ? "思考与工具调用进行中" : "正在思考"}</span>)}

> 守卫 `tests/gui/a1095-body-gate.spec.ts`（4 断言）＋ 变异 `mut-a1095s2.mjs`（5 条，**实测全捕获**）。

### 3.3 激励语换行（☆，独立小改）

`LiveStatusLine` 的布局从「一行 flex-wrap」改为**两行**：

```
第一行：[主句 status.text] · [detail]
第二行：[cheer]                     ← 独占一行，右对齐或左对齐（见下）
```

- 容器 `flexDirection: "column"`（第一行仍是 `flex` 行放主句+副句）；
- `cheer` 单独一行、`marginTop: 2`，**不再参与主句的行内流** ⇒ 彻底消除"激励语挤跑主句"的折行。
- 对齐：左对齐与主句同起点（`padding-left` 已由容器给 42px），视觉上从属清晰。

**只需 ~10 行改动**，可**立即单独落地**，不依赖 #8/#9。

## 4. 吐字动画（#5 推广 + #6 根治闪烁）

### 4.1 推广到思考内容（#5）

思考文本当前渲染在 `TimelineNode` 的 `think` 分支，**整段** `<Markdown text={cleanThink}/>`（收起态是摘要行）。
推广方案：

- 活跃组的最后一个 think 段，**流式期**其展开态正文走 `splitStreamFade` + `visibleTailUnits`
  （与正文**同一套**切分/净化，不另写一份）；
- 收起态的**摘要行**也加渐入？→ **否**。摘要行是 `white-space:nowrap` + ellipsis 的单行预览，
  加逐单元 span 会破坏 ellipsis（且它每帧变化 → 闪烁风险）⇒ **摘要行保持现状**，只对展开态生效。

**复用而非复制**：`splitStreamFade` / `visibleTailUnits` 已是纯模块，思考区直接引用即可。
⚠️ 守卫：断言思考区与正文区**共用同一实现**（防漂移，项目铁律「同一件事两个产地必然漂移」）。

### 4.2 闪烁根治（#6）

**当前机制**（A-1070 已修）：单元在**整行**上左锚定切分 ⇒ 已有单元的 `at`（React key）不随窗口滑动而变。

**残留闪烁的可能来源**（需实测确认，候选排序）：
1. **`at` 与实际文本错位**：`visibleTailUnits` 投影时若某单元被削，`at` 仍指向原位置 ——
   React key 稳定，但**同一 key 的文本长度变化**在某些情况下仍触发布局抖动。
2. **`linePrefix` 与 `settled` 的接缝跳变**：A-1080 已把接缝切在真实换行上，但**窗口滑过换行那一刻**
   仍会重排一次（`linePrefix` 从"行内"变"并入 settled"）。
3. **CSS 动画重播**：`key` 稳定但元素被 React **复用后仍重跑 animation**（若 `className` 或 `animation-name` 有抖动）。

**根治方向**（分步验证，不盲改）：
- 先加**可观测手段**（临时探针）：给每个 `stream-fade-unit` 打 `data-at`，用 MutationObserver / 渲染计数
  统计"同一 key 的单元在连续两帧间被卸载重挂"的次数 —— **先拿到证据再动手**（项目铁律）。
- 若命中 1：把 `visibleTailUnits` 的投影改成"**只允许整单元存在或整单元清空**"，
  禁止"把一个单元切成两半"（切半会导致同 key 文本长度跳变）。
- 若命中 2：把 `linePrefix` 也纳入"单元化"，让接缝恒定落在单元边界。
- 若命中 3：`animation` 用 `animation-fill-mode: forwards` + 保证 `key`/`class` 连续两帧全同。

**判据**：`tests/gui/` 新增守卫——模拟连续追加字符 N 步，断言"任一 `at` 对应的元素不应出现
'出现→消失→再出现'"（用渲染函数直接断言 `visibleTailUnits` 的**逐帧 key 集合单调不减**）。

## 5. 侧栏 token 明细（#12）

### 5.1 口径（必须写进 UI，不许假装精确）

| 阶段 | 正文 token | 推理 token | 标记 |
|---|---|---|---|
| 流式中 | `round(replyChars/4)` | `round(reasonChars/4)` | **都带 `≈`** |
| 流末（收到 `usage`） | `usage.completion_tokens` 精确值 | `completion_tokens_details.reasoning_tokens` | **去掉 `≈`** |
| 流中断（无 usage） | 保留估算 | 保留估算 | 显示"未收到 usage，此值为估算" |

⚠️ **协议事实**（调研一手结论，勿再试图"修成真值"）：`reasoning_tokens` 是 `completion_tokens` 的
**子集**（`completion = reason + visible`），**不是额外项** ⇒ 展示上必须说明"推理含在总输出内"，

### 5.4 构成算术的真实缺陷：**子集并计 ⇒ 合计虚高**（#260）

布局不是问题，**算术是**。旧四项直接相加：

```
旧：合计 = prompt_tokens + completion_tokens + reasoning_tokens + cache_read_tokens
```

其中两项是**别人的子集**：

| 子集关系 | 判据 | 出处（一手） |
|---|---|---|
| `reasoning_tokens ⊂ completion_tokens` | 本机 1651 条 usage 记录里 47 条带推理 token，**47/47 全部 reasoning < completion** | `freeze` 记录实测 + §5.1 |
| `cache_read ⊂ prompt`（OpenAI / DeepSeek 系） | `cache_read_in_prompt = true` | `core-ts/src/llm/client.ts` 的归一化分支 |
| `cache_read ∦ prompt`（Anthropic 系） | `cache_read_in_prompt = false`，两者**并列** | 同上 |

⇒ 用户截图里 sidebar「累计 tokens」= **17,007,635**，而真实量约 **8.96M** —— **虚高约 86%**。

**修法（唯一产地）**：新增纯函数 `usageComposition()`（`gui/src/renderer/pages/contextMath.ts`），
判据与**记账层** `core-ts/src/services/usage.ts` 的 `computeRecordCost` **同源**：

```ts
inputSide  = prompt + (cacheReadInPrompt ? 0 : cacheRead)   // 输入侧
outputSide = Math.max(completion, reasoning)                // 输出侧（子集不并计）
total      = inputSide + outputSide
```

`composeSegments` 同步改为**互斥四段**（输入 / 缓存读 / 输出 / 思考，和恒为 100%），
分母 = `total`。图例第 4 项 `其他` → `缓存读`（旧标签是错标）。明细改**两层**：
父项 `输入 Tokens（提示词）` / `输出 Tokens（回复）`，子项 `└ 其中 缓存读（命中）` /
`└ 其中 推理（思考）`，合计行 = `输入 + 输出`。

⚠️ **`cacheReadInPrompt` 必须落盘进累计态**（`AccumUsage` 新增该字段）：它是**协议级**属性，
不是可由其它数值反推的派生态；丢失它 ⇒ 累计态的输入侧只能瞎猜（`t.cacheReadInPrompt === 1` 判三态）。

## 1. 核心理念：Agent 永存的三层模型

**模型是硬件，Agent 是软件。** 模型不断迭代（GPT 世代更替、本地模型换代、供应商切换）、设备可能更换（主力机/便携机/新电脑）、模型服务商可以变化，但 Agent 的人格、记忆、关系应当长存——这是本架构的唯一目标。

```
┌─ 身份层（不可变）  name / role / identity_prompt / 人格档案
│    —— Agent 的"自我"，模型迭代、设备更换都不触碰这层
├─ 记忆层（累积）    memory.json / behavior archive / knowledge 晋升 / 技能
│    —— Agent 的"人生经历"，随时间增长，跨设备、跨运行时保留
└─ 模型层（可替换）  模型路由（本地 sidecar / 任意云端 API / 专用服务）
     —— 唯一会"迭代/退役"的一层：换模型 = 换大脑，不换人
```

**两条推论**（本方案的硬性约束）：
- **数据与运行时解耦**：Agent 的"灵魂"（§7 永存资产）必须与设备、语言、模型完全无关
- **一切可替换**：模型、UI、运行时、存储后端均是可换组件，唯有数据契约冻结

### 1.1 工程三层 ↔ 心智架构（L1/L2/L3）映射

Agent 内部心智分层已在 Intelligence.md §12 完整定义（L1 身份铁律 / L2 行为模式 / L3 动态心性），本文档**不重复定义**，只给出工程承载映射：

| 心智层 | 可变性 | 工程承载 | 所属工程层 |
|---|---|---|---|
| L1 身份铁律 | 完全静态、永不改变 | identity 存储（identity_prompt / iron-laws），演化引擎无权修改 | 身份层 |
| L2 行为模式 | 半固定、缓慢演化（L3→L2 沉淀） | BehaviorManager（Node）+ `behavior/` 持久化 | 身份层（可演化的半固定部分） |
| L3 动态心性（记忆/情绪/人格状态） | 完全动态、实时变化 | AffectManager（Node）+ 记忆检索注入 message 层 | 记忆层 |

映射结论：**L1+L2 是"软件人格"的工程形态（身份层），L3 是"人生经历"（记忆层）；模型层承载 L1/L2/L3 的推理执行**。模型换代时 L1/L2/L3 数据原样保留，仅推理载体更换。

## 3. 双栈整合架构：进程边界 = 工具链边界

每个进程用它擅长的语言实现，进程间用稳定协议通信；谁的语言强就让它管哪一段。

```
pilot project/                   ← 迁移仓库（git：Gcyming/local-project）
├─ core-ts/       TS：调度/会话/工具轮/沙箱决策/记忆/心智/模型生命周期（业务核心，Node 主控）
├─ gateway-ts/    TS：HTTP 网关/队列/认证/限流 + 完整服务端点（阶段 5A 升级）
├─ gui/           Electron（TS 渲染层）
├─ sidecar/       Python（**优点面，长期保留**）：推理 + 嵌入执行封装（llama-cpp-python / BGE-M3）
├─ shared/        ★契约层：openapi.yaml + zod schemas + pydantic 模型（唯一双端共享）
├─ data/          语言无关资产（永存层，schema 冻结）
└─ scripts/       双栈启动/构建/打包编排
```

各取所长对照（已确认的决策；v2.3 终局：TS 为主 + Python 优点辅助）：

| 维度 | 决策 |
|---|---|
| 模型推理（执行） | **Python 优点面**：llama-cpp-python / llama-server（已实战 Qwen 3B），经 sidecar 封装（SSE，OpenAI 兼容） |
| 嵌入（执行） | **Python 优点面**：BGE-M3（llama-cpp-python / llama-server `/embeddings`，CPU） |
| 编排/调度/检索/记忆 | **TS 为主**：模型生命周期编排、四阶段检索 Node 侧闭环（阶段 5A 起）；向量存储 LanceDB JS 或 JSONL |
| I/O 密集（网关/队列/事件流） | Node（单线程事件循环） |
| 重计算（C 扩展） | 由 llama-server 二进制承担——Node/Python 均只是编排，无语言绑定依赖 |
| CLI / dev 工具 | Node 生态（execa/commander/tui） |
| 依赖管理 | pnpm（主）+ uv（sidecar 优点面锁文件） |
| **终局语言构成** | **TS ≥ 85%**（core-ts + gateway-ts + gui + shared 主体）；**Python < 15%**（仅 sidecar 推理/嵌入执行优点面）；GitHub 语言统计为观测指标（**观测参考，非发布硬指标**，验收见 §12） |

## 4. 通信协议：单协议原则

- **数据面 + 控制面统一 HTTP/SSE**（仅绑 127.0.0.1）：
  - `/chat/completions`：流式推理，OpenAI 兼容——sidecar 可整体换成 Ollama / vLLM / LM Studio，Node 侧零改动
  - `/embeddings`：BGE-M3 嵌入，同 OpenAI 格式
  - `/health`：心跳（Node 超时即判死）；`/load_model`、`/unload_model`、`/stats`（显存/队列，直供 UI 监控面板）
- **动态端口**：Node 启动 sidecar 前 `net.createServer` 探测空闲端口 → 以 `INFER_PORT=xxxxx` 环境变量传入 → sidecar 绑定该端口；永不冲突，支持未来多 sidecar 实例（多模型并行）
- **stderr 不建管道**：直接重定向到日志文件（避开 Windows 管道缓冲区死锁；崩溃最后一行用于排障）

## 5. 依赖与工程规范

- **入口**：顶层 `pnpm run dev / build / test / contract:check`（Windows 多 shell 零摩擦）；环境变量统一 `cross-env`
- **锁文件**：`uv.lock` 与 `pnpm-lock.yaml` 均提交钉死（llama-cpp-python 版本须与显卡驱动匹配）
- **日志轮转（7×24 必修）**：Python `RotatingFileHandler`（单文件 10MB × 5 份）；Node `pino` + `pino-roll`；磁盘写满不得连锁崩溃
- **sidecar 运行形态**：开发态 uv venv；打包态 PyInstaller 保留为可选（自用 7×24 抗灾性优先；杀毒误报加白名单；CUDA 动态库 cudart64_*.dll 等需 --add-binary 时再处理）
- **模型权重永不打包**：首次启动按需下载（断点续传）或用户手动指定路径
- **契约测试本地硬门槛（无 CI 替代）**：`contract:check` 串行 = zod 编译校验 → pydantic 导入校验 → openapi 生成类型假数据双端互验；任一步失败，`dev`/`build` 拒绝启动

## 6. 关键策略

### 6.1 ModelRouter：多模型统一路由（多模型诉求的落点）

```
请求 → Router(任务类型, Agent能力需求, 设备状态)
         ├─ chat/embedding/image/video 按任务类型路由
         ├─ 设备状态：显存余量、网络可达性、成本档位
         ├─ 降级链：primary → fallback（本地 OOM → 云端；付费 → 免费）
         └─ 注册表：任意 OpenAI 兼容 API / 本地 GGUF / 专用服务（如 Agnes）统一注册
```

- **Agent 与模型彻底解耦**：Agent 只声明能力需求（如"需长上下文模型"、"需生图能力"），路由层按"设备 + 任务 + 成本"解析到具体模型——同一 Agent 在主力机跑本地 7B、在便携机跑云端 API，人格不变
- 由现有 provider 体系（inherit/api/local）演进而来

### 6.2 显存策略（按实际硬件，不预设）

BGE-M3 嵌入走 CPU（延迟不敏感，显存全留给推理模型）；推理模型 LRU 卸载。

### 6.3 data/ 单写者

Node 为唯一写入方，Python 只读；向量索引更新由 Node 发指令执行。

### 6.4 Prompt 组装：双路径注入（对齐 Intelligence.md §12）

```
system prompt（固定注入）   ← L1 身份铁律 + L2 活跃行为模式 + 当前情绪/人格状态
                              （严格 token 预算，每次请求固定注入，永不裁掉 L1）
message 层（检索注入）     ← L3 记忆检索结果（向量召回种子 → 双向链接遍历 →
                              标签过滤 → 艾宾浩斯权重排序，详见 Intelligence.md）
                              （按需注入，不占用固定 token 预算）
```

- 由 Node 侧 prompt 构建模块统一组装；sidecar 不接触 prompt 组装
- **记忆检索采用四阶段策略**（向量种子 → 链接遍历 → 标签过滤 → 权重排序）。**过渡期（阶段 5A 完成前）**四阶段全链路在 sidecar 检索 API 内闭环；**阶段 5A 起改为 Node 侧闭环**（core-ts 检索服务直管向量存储；嵌入经 sidecar `/embeddings`）——禁止退化为纯向量 topK，禁止绕过四阶段链路直查向量库
- **向量存储选型（评审 P0-2，v2.4；规格扩展 v2.8）**：5A.2 开工前 2 小时 spike 定案——1000 条模拟记忆实测四阶段检索延迟，对比 LanceDB JS / JSONL / better-sqlite3+向量列，**三选一写死本节，不留"或"**；结论回填本节。**扩展验证维度（v2.8）**：① 批量写入性能（万条级写入耗时）② **10 万条量级性能衰减**（记忆是永存资产，持续增长，不能以小数据量定案）③ **Windows 原生依赖安装/编译兼容性**（LanceDB JS 等原生模块在 Windows 坑较多，需在 spike 中实测 `pnpm add` + 加载即跑通）
- **✅ 向量存储 spike 定案（v2.8，2026-08-18 实测）：LanceDB（@lancedb/lancedb）**。实测数据（1024 维模拟记忆，Windows 本机）：

  | 维度 | LanceDB | JSONL 全内存 | better-sqlite3+暴力余弦 |
  |------|---------|-------------|------------------------|
  | 1000 条写入 | 79ms | 154ms | 18ms |
  | 1000 条检索（10 次平均） | 8.8ms（无索引） | 2.4ms | 2.2ms |
  | 10000 条写入 | 600ms | 1.39s | 106ms |
  | 10000 条检索（ivf_pq 索引） | 5.9ms | ~20ms | 18ms |
  | 100000 条写入 | 5.95s | 外推 ~15s | 外推 ~1.8s |
  | 100000 条检索 | **8.7ms**（1000→100k 增速 ×0.99，ANN 亚线性） | 外推 ~238ms | 外推 ~215ms |
  | Windows 兼容性 | ✅ pnpm add + 加载即跑通 | 纯文件无依赖 | ✅ 需 pnpm-workspace.yaml `allowBuilds` 放行 |

  **定案理由**：① 记忆是永存资产持续增长，LanceDB 原生 ANN 索引 10 万条量级检索恒定 ~9ms 亚线性，暴力余弦方案线性恶化至 200ms+；② LanceDB 为 Rust 原生实现，异步执行不阻塞 Node 主线程（JSONL 全内存暴力检索会阻塞 Agent 事件循环）；③ Windows 原生加载实测通过；④ links/tags/importance/ts 直接作为列可组合过滤。**代价**：写路径稍慢（万条 600ms）与 10 万条建索引 45s，均后台异步可接受。**落地约束**：5A.2 起记忆向量库固定 LanceDB（`data/{agent_id}/lancedb/`），不再使用 JSONL/sqlite 向量方案；embedding 维度 1024（BGE-M3）写入 schema 校验，防 A-027 类维度漂移复现。

### 6.5 AffectManager（Node）：情绪网络

纯计算逻辑（信号 → PAD delta → 最近邻 mood → 指数衰减回基线），不需要模型推理、不需要向量库：

- 接收情绪信号（工具成败、用户情绪、novelty 等）→ 叠加 PAD 状态 → 指数衰减 → 判定当前 mood
- 持久化 `emotion.json`；提供当前 mood 给 prompt 组装模块（§6.4 固定注入路径）
- **sidecar 不参与情绪计算**

### 6.6 BehaviorManager（Node）：行为生命周期

L2 行为模式的 CRUD + 状态机（形成 → 稳定 → 微调 → 淡出 → 归档 → 场景重现 → 再巩固）：

- 管理 `behavior/` 下 patterns.json / traits.json / evolution_log.jsonl
- 双轨召回（活跃行为 + 归档行为同时检索，供 §6.4 固定注入）
- **预留影子模式接口**：行为定义含 `shadow: bool` 字段——影子行为执行结果记入 evolution_log 但不对外生效（第 1 阶段不实现，仅接口预留）

### 6.7 并发安全策略（评审 P1-3，v2.4 新增）

> 事实修正：阶段 4 的 worker_threads 是**隔离上下文 + 消息通信**（workerData/messagePort，无 SharedArrayBuffer），**不是** Python 多进程语义的直接翻译，无内存共享竞态；本节约束服务端组装期（5A/5B）的并发纪律与验收。

- **单写者铁律**：data/ 下全部文件（agents.json / memory / audit.jsonl / 记忆索引）唯一写入方为主进程（Node）；Worker/线程只发消息，由主进程统一落盘（对齐 §6.3）
- **审计串行化**：audit.jsonl 由主进程单点追加写（worker 经消息通道上报），杜绝多线程交错写
- **共享状态保护**：Agent 状态/会话状态在主进程内存中单所有权，**不传共享引用进线程**；跨线程数据仅经消息序列化传递
- **锁**：进程内互斥用 `async-mutex`；跨进程协调走 HTTP 端点语义，不用文件锁
- **压测用例**：补 3-5 个并发 vitest 用例（多 worker 同写一文件、并发 swarm 任务不交错、audit 串行追加）纳入 5A 验收

## 7. 数据契约与多设备同步（永存资产，schema 冻结）

### 7.1 永存资产清单

**永存双根**：`Knowledge/`（人读资产，Obsidian vault）与 `data/agents/`（机器状态）并列，均为永存根；下表清单以实际落盘路径为准校准，**导出清单由机器自动推导（§7.2），不依赖人工维护**。

| 资产 | 内容 | 丢失后果 |
|---|---|---|
| `config/agents.json` | 身份/关系（L1/L2 引用） | Agent 消失 |
| `Knowledge/` | L3 心性档案（Obsidian vault：知识/规则/技能晋升/图谱拓扑 knowledge.json） | 记忆网络退化为扁平列表 |
| `data/agents/{id}/agent.json` | Agent 元数据 | 元数据丢失 |
| `data/agents/{id}/identity/` | L1 身份铁律 | 身份重置 |
| `data/agents/{id}/behavior/`（patterns/traits/evolution_log） | L2 行为模式 + 演化历史 | 行为模式重置，等于换了个人 |
| `data/agents/{id}/memory/` | 对话记忆（working + long_term） | 记忆丢失 |
| `data/agents/{id}/emotion.json` | 当前情绪状态（PAD + mood） | 情绪重置为基线 |
| `data/agents/{id}/persona_state.json` | 人格短期状态 | 人格状态丢失 |
| `data/agents/{id}/relationships/` | 用户画像 + 关系叙事历史 | 关系感丢失 |
| `data/agents/{id}/archive/` | 降级归档（行为/沉睡记忆） | 历史不可回溯 |
| `~/.slime_pass`、`providers.enc.json` | 密钥 | **永不入包**（§8.5 排除清单） |

**永不删除铁律**（对齐 Intelligence.md）：
- 记忆：只调整艾宾浩斯检索权重，**不删除记录**；沉睡记忆可被关键词唤醒
- 行为：降级 = 从活跃层移至 `archive/`，**不删除**
- 向量索引：只 upsert，不做 delete（delete 仅用于修正写入错误，不用于"遗忘"）

**记忆存储格式约束**：记忆条目必须包含 `links` 字段（Obsidian 双向链接语义），支撑四阶段检索的链接遍历（§6.4）。

**永存资产 = 唯一需要跨设备携带的东西**；程序、模型、设备配置都不是。

### 7.2 身份移民协议（跨设备/跨运行时/灾难恢复）

- **导出**：一键打包 Agent 全量状态 → 单文件（格式自定，如 `.slimeagent` 压缩包，含清单 + 校验和）
- **导入**：在新设备/新环境恢复——"移民"后 Agent 拥有完整人格与记忆
- 这是多设备的第一公民能力，也是"应用可搬家"的基础
- **兼容规则（v2.8）**：**向前兼容为强制**（新版本可导入旧版本导出的包，含 manifest 版本号 + 迁移钩子）；向后兼容为尽力而为（旧版本遇更高版本 manifest 明确报错并提示升级，不静默半导入）；**增量导出为规划项**（全量包随记忆增长变大，长期支持按时间/资产类型增量导出 + 增量合并，v1 先做全量，增量在收尾期规格中定案）

**导出清单自动推导（约束 + 规则，禁止人工维护）**：

> 导出清单由程序扫描两个永存根（`Knowledge/` 与 `data/agents/`）自动生成——凡不在敏感排除清单（§8.5 同款：`providers.enc.json` / `*.slime_pass*` / `auth_token*` / `*.enc`）内的文件全部入包；**禁止人工维护导出清单**（人工清单必漏项，机器扫描 + 排除是唯一保证完整性的方式）。

### 7.3 多设备同步规则

- **设备角色**：主设备（权威写入）/ 从设备（只读 + 离线编辑，定期合并）
- **同步通道由用户自选**（git 仓库 / 云盘 / 局域网 / USB）——框架只保证"导出/导入 + 合并规则"，不绑定任何云服务
- **冲突策略**：`agents.json` 以主设备为权威（单主写原则的跨设备延伸）；`Knowledge/`、记忆按文件 + 时间戳合并；冲突副本留存不静默覆盖
- **设备配置独立**：模型路由、显存、端口等设备本地配置不进同步——同一套 Agent 数据在不同设备上按各设备能力运行

## 8. 成品封装：可更新、可自建环境的完整应用

### 8.1 目录布局（三区分离）

```
安装区（只读，更新时整区替换）
├─ 应用（core/gateway/gui 打包产物）
└─ sidecar（sidecar/ 打包产物，版本独立）

数据区（用户可写，永存资产，独立于安装区）
├─ agents.json / Knowledge/ / data/ 记忆
└─ 设备配置（模型路由、端口、日志）

模型区（可选外部路径，权重不打包）
└─ 本地 GGUF 模型（按需下载或手动指定路径）
```

三区分离的意义：**升级应用不动数据，迁移数据不带程序**。

### 8.2 双路线安装

| 路线 | 形态 | 适用 |
|---|---|---|
| 全量安装版 | 官方打包（Windows 安装器，含 sidecar，electron-builder；官方推荐 Forge，遇坑可切换，§9 阶段 5） | 快捷部署、自动更新 |
| 便携版 | 解压即用（同一打包产物变体，7×24 抗灾优先） | 应急/多机快速携带 |

两条路线共享同一套数据契约与配置模板——自建环境产出的数据可直接被发行版读取，反之亦然。

> **已确认**：GUI 用 Electron；打包双形态 = 全量安装版 + 便携版各一份；双形态统一受 §8.5 敏感文件门禁约束（构建扫描检出即中止）。

### 8.3 更新机制

- **应用自更新**：electron-updater / tauri updater，签名校验，增量下载；应用区整区替换，数据区零触碰
- **sidecar 独立版本**：Python 推理服务可与主程序错峰更新（模型后端演进不阻塞 UI）；更新前契约测试保证双端兼容
- **数据迁移通道**：schema 冻结为原则；若未来必须演进，提供版本化迁移脚本（升级前自动备份）
- **回滚**：更新包保留上一版本，异常自动回滚

### 8.4 多设备分发

同一发行包支持任意设备；设备间只同步永存资产（§7）；新设备部署 = 安装应用 + 导入身份（§7.2）两步。

### 8.5 打包安全检查（硬性门禁）

**安装区产物绝不允许夹带任何用户敏感文件。** 构建/打包脚本执行前，必须扫描安装区内容，检出以下排除清单中的任何文件即**立即中止构建并报错**：

```
providers.enc.json
*.slime_pass*
auth_token.json / auth_token.enc
*.enc / *.secret / *.key
```

- 双路线（发行版/自建环境）同样受此门禁约束
- 该检查为机器强制（脚本内置），不依赖人工自觉——即使未来某个环节手滑，打包也不会产出夹带密钥的产物

- **进程映射与对接方式（官方文档核验，v2.5；边界定案 v2.6）**：
  - **主进程**（完整 Node）：core-ts 调度核心（会话/工具轮/心智/检索）+ sidecar spawn 管理（model_server.ts）+ 窗口/生命周期

  - **Preload + contextBridge**：唯一桥接；注意 **sandbox 开启时 preload 仅可用 electron 子集**（ipcRenderer/contextBridge，不能 require 任意模块）——本项目够用
  - **core-ts / gateway-ts 边界（v2.6 定案）**：**core-ts = 唯一调度核心（库形态）**，含服务层 Service API（ChatService / SwarmService 等，事件流输出，可同时被 HTTP 适配与 IPC 消费）；**gateway-ts = HTTP 适配薄壳**（import 同一份 core-ts，仅做认证/限流/CORS/SSE 传输转换，**不含独立调度逻辑**）——不存在两个调度核心；**gateway-ts 经函数调用访问 core-ts（非 HTTP 回环），无额外端口/网络开销**——因此不做 nginx 式独立代理
  - **事件流统一格式（v2.6）**：core-ts 服务事件统一为 `{ seq, type, data }` 序号事件对象——IPC（结构化克隆）与 SSE（JSON）同传同一格式；SSE 客户端断线凭 `seq` 重连补漏
  - **主进程负载压测（v2.8）**：主进程承载调度核心 + sidecar 管理 + 窗口——**重计算（四阶段检索/行为计算等 CPU 密集段）默认放 worker_threads**（§6.7 消息隔离基础已有），主进程仅事件协调与转发；阶段 5 开工前实测：长对话 IPC 流式序列化开销（100K 字符级）与检索峰值是否阻塞主进程，超阈值则检索服务整块 worker 化
  - **运行时关系**：Electron 运行时 **gateway-ts 进程不启动**，生产态调度全部走主进程内 core-ts 实例；gateway-ts 仅在 CLI、外部接入、开发态启用
  - **GUI → 调度**：走 IPC（不经过 HTTP）；渲染层经 `window.electronAPI` 调主进程内 core-ts 服务；流式经 IPC 事件转发
  - **远程接口预留（v2.6）**：生产态 gateway-ts HTTP 接口**默认关闭、可选启用**——为未来远程访问/多客户端/多设备协同预留入口，不增加当前复杂度
  - **跨语言边界不变**：主进程 ↔ sidecar 走 localhost HTTP/SSE（§4 单协议原则）

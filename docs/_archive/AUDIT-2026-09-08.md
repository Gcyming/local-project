## 一、真实缺陷（按严重度）

### 【高危-1】子 Agent 沙箱逃逸：workspace 被清空 = 全放行

**位置**：`core-ts/src/sandbox.ts:720`

```ts
const parentCfg = this.getAgentConfig(info.parent_id);
cfg = parentCfg.inherit_from_parent ? { ...parentCfg, workspace: "" } : this.config;
```

**为什么是洞**：

| 位置 | 语义 |
|---|---|
| `sandbox.ts:355-357` | `validateWorkspace()`：`if (!workspace \|\| !target) return !workspace` → **空串 = 不限制，返回 true** |
| `sandbox.ts:474` / `:567` | `if (cfg.workspace && target && !validateWorkspace(...))` → **workspace 为空时整段校验被跳过** |
| `sandbox.ts:203` | `inherit_from_parent: true` 是默认值 |

⇒ 任何带 `parent_id` 的子 Agent（fork worker / swarm subtask / `delegate_subagent`）
的文件路径限制**全部失效**，可读写任意路径。

**触发条件**：仅当用户配置了 `sandbox.workspace` 时暴露。默认值 `workspace = ""`
本就是不限制，此时无影响——但一旦用户设了工作目录做隔离，子代即绕过。

**业界对照**（已查证 Claude Code 官方语义）：subagent **继承父代授权**，且父代运行时
授予的 `additionalDirectories` **不向子代传播** —— 子代权限 ⊆ 父代，永远只能更严。
slime 当前实现正好相反。

**建议修法**：
```ts
// 子代 workspace 取父代原值；父代未设则回退全局，不得置空
cfg = parentCfg.inherit_from_parent
  ? { ...parentCfg, workspace: parentCfg.workspace || this.config.workspace }
  : this.config;
```
更彻底：把 `""` 的语义从「不限制」改为「未设置 → 回退全局配置」，消除 fail-open 歧义。

### 【高危-2】主链路无引擎源码写入保护（双栈迁移回归）

**位置**：`core-ts/src/tools/classifier.ts:71-109`

`SENSITIVE_FILES` 是**文件名集合**：
```
.slime_pass / providers.enc.json / auth_token.enc / auth_token.json
slime.toml / agents.json / global_config.json / history.jsonl / audit.jsonl
.git/config / passphrase / password / id_rsa / id_ed25519 / .pem / .p12 / .pfx
```

**没有目录级保护**。写 `core-ts/src/sandbox.ts`、`gui/src/main/index.ts`、
`shared/openapi.yaml` → 落到 `:109`「工作区内普通写入」→ **auto 自动放行**。

⇒ Agent（或被 prompt injection 劫持的 Agent）可改写自己的护栏代码与宿主主进程。

**这是回归**：被它替换的 Python 侧有目录级保护——`tools/builtin.py:107`
```python
_WRITE_BLOCKED_DIRS = ("config", "core", "tools", "social", "tests")
```
主链路（TS）比被替换掉的旧链路（Python）更弱。

**干净的例外**：路径穿越 `..` 在 `:102` 有正确拦截。

**建议修法**：新增 `PROTECTED_DIRS`（目录前缀匹配，写 → block）：
`core-ts/`、`core/`、`gui/src/main/`、`sidecar/`、`shared/`、`tools/`、`config/`、
`.git/`。密钥类走加密存储，源码类走只读挂载或写前二次确认。

### 【中高-3】审计日志不可靠：内存态覆写磁盘 + O(n²)

**位置**：`core-ts/src/sandbox.ts:395`、`:801-820`

```ts
private auditLog: AuditEntry[] = [];          // :395 从不从磁盘加载
if (this.auditLog.length % 200 === 0) void this.rotateAuditLog();
async rotateAuditLog() {
  const kept = this.auditLog.filter(...);
  await writeFile(path, kept.map(...).join("\n"));   // :815 全量覆写
}
```

**问题**：
1. 进程重启后 `auditLog` 为空，新会话攒到 200 条时，`writeFile` 用**仅内存中的 kept**
   整体覆盖磁盘文件 ⇒ 历史审计记录被静默清空（`:818` catch 还吞掉异常）。
2. 每 200 条全量重写整个文件 ⇒ O(n²) 写放大。当前 `data/audit.jsonl` 27858 行 / 8.7MB。

审计日志本应 append-only —— 它是安全事件溯源依据，被覆盖等于失去意义。

**建议修法**：
- 启动时 `readFile` 回载（或改用按天分片 `audit-YYYY-MM-DD.jsonl`）
- 轮转改为**按日期切分文件**，不再全量重写
- 或引入 `pino`/`winston` 的 WAL 式 append + size-based rotation

### 【高危-6】生产包默认开放 CDP 远程调试端口 9222（已用构建产物证实）

**位置**：`gui/src/main/index.ts:3516-3518`

```ts
if (process.env.NODE_ENV !== "production") {
  app.commandLine.appendSwitch("remote-debugging-port", "9222");
}
```

**证据链**（三步全部核实）：
1. 全仓 `gui/` 内**没有任何地方给 `NODE_ENV` 赋值**——只有 index.ts:3517 与
   updater.ts:68 两处**读取**，构建脚本（electron-vite build）未注入该变量。
2. 构建产物 `gui/out/main/index.js` 中该判定**原样保留**，Vite 未做静态替换：
   `if (process.env.NODE_ENV !== "production") { electron.app.commandLine.appendSwitch("remote-debugging-port","9222"); }`
3. ⇒ 打包后运行时 `process.env.NODE_ENV === undefined` → 条件为 true → **正式版默认开 9222**。

**影响**：本机任意进程可经 CDP 附到渲染层，执行任意 JS、读取全部 IPC 流量、
窃取内存中解密后的 API Key 与 passphrase。属本地提权。

**修法**（Electron 官方推荐写法）：
```ts
if (!app.isPackaged) { app.commandLine.appendSwitch("remote-debugging-port", "9222"); }
```

### 【高危-7】ChatPanel 每次渲染泄漏一个 IPC 监听器

**位置**：`gui/src/renderer/pages/ChatPanel.tsx:1994-2004`

```tsx
  }, [agentId, makeMessage]);          // ← useEffect 已在 :1991 结束
  const off4 = (() => { ... return fn((ev) => {...}); })();   // ← :1994 组件函数体，非 effect 内
```

- `off4` 在**组件函数体**中创建 ⇒ 每次重渲染都新增一个 `slime:chat:streamEnded` 订阅
- :1989 的 cleanup `off1();off2();off3();off4()` 闭包捕获的是**首渲染**那次的 off4
- effect deps 仅 `[agentId, makeMessage]`，不随渲染重跑 ⇒ 后续订阅永不解绑

流式输出每 50ms 节流 setState ⇒ 每分钟新增上千个监听器，事件派发 O(n) 累积，长时间会话必然卡死。

**修法**：整块挪进 :1661 的 useEffect 内部，作为常规 `off4` 订阅。

### 【高危-8】主进程无 unhandledRejection 兜底 + 两处裸 Promise

**已确认**：`gui/src/` 全量 grep **零** `process.on("unhandledRejection" | "uncaughtException")`。
Node 默认 throw 模式 ⇒ 任何未捕获 rejection 直接终止主进程（整个应用退出）。

两处裸 Promise：
- `main/index.ts:2544-2547` — `statsPoll = setInterval(async () => { const snap = await statsService!.snapshot(); ... }, 3000)`
  无 try/catch；`statsService!` 非空断言在 poll 早于 `ensureServices()` 完成时同步 TypeError。
  后端 sidecar 挂掉/重启期间每 3 秒一次 ⇒ 崩溃。
- `main/index.ts:1015-1022` — `void mgr.startEmbedding().then((r) => {...})` 外层缺 `.catch()`
  （内层 :1017 有）。bge 下载完成回调触发，启动失败即崩主进程。

**修法**：回调内 try/catch；注册全局 `process.on("unhandledRejection")` 记录后继续（不退出）。

## 1. 目标与原则

**目标**：将单个 Agent（含人格、记忆、行为模式）完整打包，支持跨设备/跨运行时迁移，恢复后拥有完整人格与记忆。

**原则**：

1. **机器自动生成清单**：导出清单由程序扫描永存资产根目录自动生成，**禁止人工维护**（人工清单必漏项）
2. **SHA-256 校验和**：每个文件在 manifest 中有对应校验和，导入时逐项验证
3. **向前兼容强制**：新版本必须能导入旧版本导出的包（含 manifest 版本号 + 迁移钩子）
4. **向后兼容尽力**：旧版本遇更高版本 manifest 明确报错并提示升级，不静默半导入
5. **增量导出为规划项**：v1 先做全量，增量导出/合并规范在收尾期定案

## 2. 包格式

- **格式**：ZIP 压缩包，扩展名 `.slimeagent`
- **内部结构**：顶层为 `manifest.json`，其余为永存资产目录
- **压缩级别**：默认 deflate level 6（平衡速度与体积）
- **加密**：包内文件**不加密**（敏感信息如 passphrase/providers.enc.json 永不入包）

### 2.1 包内目录结构

```
example-agent.slimeagent
├── manifest.json                          ← 包描述 + 校验和清单（必须在顶层）
├── config/
│   └── agents.json                        ← 单条 Agent 完整对象（从注册表提取，非整库拷贝，见 §4.2）
└── Knowledge/
    └── Agent Memory/
        ├── agent_<id>/
        │   ├── memory.json                ← L3 记忆（facts + links/backlinks 图谱）
        │   └── knowledge.json             ← 知识模式 patterns（懒创建，可能缺席）
        ├── global/
        │   └── knowledge.json             ← 全局知识模式（懒创建，可能缺席）
        ├── rules/
        │   └── rule_<hash>.md             ← 共享行为规则（懒创建；v1 保守全量入包）
        ├── generated_skills/              ← 知识晋升生成的技能（懒创建，可能缺席）
        └── reviews/
            └── review_<stamp>.md          ← 知识周期审查报告（懒创建，可能缺席）
```

**目录名与文件名均作为 manifest 中 `path` 字段的值**，相对路径以包根为基准。

**懒创建语义**：`knowledge.json` / `global/` / `rules/` / `generated_skills/` / `reviews/` 仅在该 Agent 实际产生对应资产时落盘（见 §2.2 真相源）。导出按**实际存在**扫描，manifest 不预列不存在的文件；导入时缺失即视为该 Agent 无此资产，不报错。

### 2.2 永存资产真相源与派生索引

包结构以 **core-ts 代码为唯一真相源**（人工记忆的路径不可信，下表为逐处核验结果）：

| 资产 | 包内路径 | 代码真相源 | 懒创建 |
|------|---------|-----------|--------|
| Agent 身份/关系/情绪/行为 | `config/agents.json` | `core-ts/src/services/agents.ts`（`AGENTS_PATH`；emotion/behavior 为内嵌字段，见 `mind/emotion.ts` / `mind/behavior.ts` 序列化兼容注释） | 否 |
| L3 记忆 | `Knowledge/Agent Memory/agent_<id>/memory.json` | `core-ts/src/memory/store.ts`（`KNOWLEDGE_MEMORY_DIR`；旧 `data/{id}/` 位置自动迁移） | 首条记忆时创建 |
| 知识模式 | `Knowledge/Agent Memory/agent_<id>/knowledge.json` | `core-ts/src/memory/knowledge.ts`（`jsonPath`；旧 `data/{id}/` 位置自动迁移） | 是 |
| 全局知识模式 | `Knowledge/Agent Memory/global/knowledge.json` | 同上（`agentId` 空串 → `global/`） | 是 |
| 共享规则 | `Knowledge/Agent Memory/rules/rule_<hash>.md` | 同上（锚定 `baseDir` 顶层，**非 per-agent**） | 是 |
| 生成技能 | `Knowledge/Agent Memory/generated_skills/` | 同上（锚定 `baseDir` 顶层） | 是 |
| 审查报告 | `Knowledge/Agent Memory/reviews/` | 同上 | 是 |
| 向量索引 | `data/{agent_id}/lancedb/` | `core-ts/src/memory/store.ts`（`lancedbUri`） | **派生索引，永不入包** |

**Knowledge/ 与 data/ 的关系**：`Knowledge/` 是人读永存根（Obsidian vault 语义，JSON + Markdown 为真相源）；`data/` 是机器运行时根（向量索引、模型注册表、MCP 缓存等）。`data/{id}/lancedb` 虽与 Agent 关联，但属于**可从 memory.json 全量重建的派生索引**（重嵌入即可，符合"向量只 upsert"铁律），因此不入包——导入方按 `rebuild_hints` 本地重建（见 §5）。

> 注：长存架构规划 §7.1 中的 `data/agents/{id}/identity/` 等拆分目录为**愿景目标态**，当前实现为 agents.json 内嵌 + Knowledge/ 外置大脑。未来若落盘布局调整，通过 `layout_version` + `migration_hooks` 平滑迁移（见 §7），不改变本协议的兼容承诺。

**Knowledge/ 与 Obsidian vault 的边界**：`Knowledge/` 目录本身可被用户作为 Obsidian vault 打开（vault 根 = `Knowledge/`），Obsidian 会在其中创建应用自有目录（核验自官方《Obsidian 的储存机制》）：根级 `.obsidian/`（仓库设置/插件/主题/热键/工作区布局）与 `.trash/`（Obsidian 回收站，若开启"移动到 Obsidian 回收站"）。这些是**应用运行时状态，不是 Agent 永存资产**：

- 导出扫描排除 `.obsidian/**`、`.trash/**`（已列入 §6 排除清单）
- 导入**不写入**这些目录，避免与目标设备上已打开的 vault 冲突
- 协议只携带 vault 的**数据文件**（memory.json / knowledge.json / rules/*.md / generated_skills/ / reviews/）；vault 元数据（链接图谱缓存、主题配置、工作区布局）由 Obsidian 自身按需重建
- 用户不开启 Obsidian 时上述目录不产生，协议不受影响；当前仓库 `Knowledge/` 下亦无 `.obsidian/`（仅 `Agent Memory/`）

## 3. manifest.json Schema

```json
{
  "schema_version": "v1",
  "layout_version": 1,
  "export_version": "1.2.0",
  "exported_at": "2026-08-18T12:00:00Z",
  "exporter": {
    "slime_version": "0.1.0",
    "runtime": "python|typescript",
    "platform": "win32|darwin|linux"
  },
  "agent": {
    "id": "agent_b1ecaa9c",
    "name": "Slime",
    "role": "编程与系统助手，负责代码任务拆解、工具调用与工程决策"
  },
  "rebuild_hints": ["lancedb"],
  "checksums": {
    "sha256": {
      "config/agents.json": "<hex>",
      "Knowledge/Agent Memory/agent_b1ecaa9c/memory.json": "<hex>",
      "Knowledge/Agent Memory/agent_b1ecaa9c/knowledge.json": "<hex>",
      "Knowledge/Agent Memory/global/knowledge.json": "<hex>",
      "Knowledge/Agent Memory/rules/rule_29fcc83f.md": "<hex>"
    }
  },
  "migration_hooks": []
}
```

### 3.1 字段定义

| 字段 | 类型 | 必须 | 说明 |
|------|------|------|------|
| `schema_version` | string | ✅ | 协议版本号，当前值 `"v1"` |
| `layout_version` | integer | ✅ | 永存资产落盘布局版本（当前 `1` = §2.1 结构）；布局变更时递增并配 migration_hooks |
| `export_version` | semver | ✅ | 包的实际版本号，格式 `MAJOR.MINOR.PATCH` |
| `exported_at` | ISO 8601 | ✅ | 导出时间戳 |
| `exporter` | object | ✅ | 导出环境信息 |
| `exporter.slime_version` | string | ✅ | slime 版本号 |
| `exporter.runtime` | string | ✅ | `"python"` 或 `"typescript"` |
| `exporter.platform` | string | ✅ | `"win32"` / `"darwin"` / `"linux"` |
| `agent` | object | ✅ | Agent 标识 |
| `agent.id` | string | ✅ | Agent ID（`agent_` + 8 位 hex，核验自 `core/agent.py` id 生成） |
| `agent.name` | string | ✅ | Agent 名称 |
| `agent.role` | string | ✅ | Agent 角色描述 |
| `rebuild_hints` | string[] | ❌ | 导入后需本地重建的派生索引（如 `["lancedb"]`）。**缺席（旧版 v1.0 包）默认 `["lancedb"]`**——向量索引为恒需派生物，导入方一律重建，保证旧包导入后检索功能完整 |
| `checksums` | object | ✅ | 文件校验和 |
| `checksums.sha256` | map\<string, string\> | ✅ | path → SHA-256 hex |
| `migration_hooks` | array | ❌ | v2+ 迁移钩子（v1 为空数组） |

### 3.2 checksums 计算规则

- 对包内每个文件（排除 `manifest.json`）按**路径字典序**读取内容
- SHA-256 作用于文件原始字节（UTF-8 编码的 JSON 字符串）
- manifest 中 `checksums.sha256` 的 path 键与包内相对路径**严格匹配**（大小写敏感）

## 4. 导出流程

```
1. 校验目标 Agent 存在于 config/agents.json
2. 从 config/agents.json 提取该 Agent 单条完整对象（见 §4.2）
3. 扫描白名单永存根（agent_<id>/ 目录 + 共享目录，见 §4.1）
4. 生成文件清单（叠加敏感排除清单双保险，见 §6）
5. 对每个文件计算 SHA-256
6. 组装 manifest.json（含 layout_version 与 rebuild_hints）
7. 将所有文件打包为 ZIP（压缩级别 6）
8. 重命名为 .slimeagent
```

### 4.1 自动清单推导规则（白名单扫描根）

```
清单 = 白名单扫描根下实际存在的文件
     ├─ config/agents.json        → 仅提取目标 Agent 单条对象（§4.2，非整文件拷贝）
     ├─ Knowledge/Agent Memory/agent_<id>/**   （memory.json / knowledge.json / …）
     ├─ Knowledge/Agent Memory/rules/**        （共享规则，v1 保守全量）
     ├─ Knowledge/Agent Memory/global/knowledge.json（若存在）
     ├─ Knowledge/Agent Memory/generated_skills/**（若存在）
     ├─ Knowledge/Agent Memory/reviews/**      （若存在）
     - 敏感排除清单（§6，双保险）
     - 空目录（无文件则不记录）
```

**禁止**：人工维护导出清单（硬编码路径列表）。程序必须从文件系统动态扫描。

**白名单优先于黑名单**：导出器只从上述扫描根取文件，仓库其余路径（`data/`、`config/skills/` 等）**天然不可能入包**——这比"全仓库扫描 + 黑名单排除"更强：新增运行时目录不会意外泄漏进包。§6 的排除清单仅作双保险（防扫描根内未来新增敏感文件）。

### 4.2 agents.json 单条提取语义

`config/agents.json` 是**全量注册表**（数组，含所有 Agent）。导出单 Agent 时：

1. 读取注册表，按 `id` 定位目标 Agent 对象
2. 包内 `config/agents.json` 写入 `[<该 Agent 完整对象>]`（单条数组，含 name/role/identity_prompt/emotion/behavior/children/parent 等全部字段）
3. **绝不**整库拷贝（会把其他 Agent 的资产带进包，违反最小暴露原则）

导入时按 conflictStrategy（§5.2）处理同名冲突：abort 报错 / overwrite 替换该条目 / keep-old 跳过；目标库其他 Agent 条目**始终不受影响**。实施计划 v1.1 阶段（多 Agent 批量导出，见 §9）即多条数组，语义自然扩展。

### 4.3 导出写入 / 导入合并 双向对应

同一份 `config/agents.json` 在导出与导入两端处理方式**严格对称**（实施时必须成对实现，只做一侧会造成不对称破坏）：

| 资产 | 导出端 | 导入端 |
|------|--------|--------|
| `config/agents.json` | 读全量注册表 → 按 `id` 过滤 → 包内写 `[<单条>]`（§4.2） | 读目标注册表 → 按 conflictStrategy（§5.2）处理 → 写回**完整**注册表 |
| `Knowledge/Agent Memory/agent_<id>/**` | 按白名单根原样扫描入包（§4.1） | 按 conflictStrategy 处理同名文件后解压 |

**不做反向拷贝**：导出永不因"目标端可能已有其他 Agent"而带上整库；导入永不因"包内含单条"而整体替换目标注册表文件。两端均以**单条 Agent 为操作单元**。

## 5. 导入流程

```
1. 打开 .slimeagent ZIP
2. 读取顶层 manifest.json
3. 校验 schema_version 与 layout_version 是否受支持
4. 逐项校验 SHA-256（缺失文件 → 报错终止）
5. 校验 export_version 兼容性（见 §7）
6. 执行 migration_hooks（如有）
7. 解压文件到目标路径（保留目录结构；config/agents.json 按 §4.3/§5.2 合并，操作单元 = 单条 Agent，不动目标库其他 Agent）
8. 验证目标路径下所有文件已写入
9. 按 rebuild_hints（缺席默认 `["lancedb"]`）重建派生索引（lancedb：从 memory.json facts 重新嵌入，只 upsert）
```

### 5.1 导入校验失败处理

| 失败原因 | 处理方式 |
|----------|---------|
| manifest.json 不存在 | 报错：非合法包 |
| schema_version 不支持 | 报错：协议版本不兼容 |
| layout_version 高于当前支持 | 报错：资产布局过新，需升级 slime 版本 |
| SHA-256 不匹配 | 报错：文件损坏或被篡改 |
| 目标路径已有同名 Agent | 按 conflictStrategy（§5.2）处理：abort 报错 / overwrite 替换 / keep-old 跳过；默认 abort |
| 文件写入后校验失败 | 报错：导入中断，回滚已写入文件 |

### 5.2 同名 Agent 冲突策略

冲突判定：包内 Agent 的 `id` 已在目标注册表中存在（对应 §8.2 `conflictStrategy`，默认 `abort`）：

| 策略 | 行为 |
|------|------|
| `abort`（默认） | 直接报错，**零写入**，不产生半导入状态 |
| `overwrite` | 包内条目替换目标条目（同 id）；该 Agent 的 memory.json / knowledge.json / rules 等资产文件整体替换为包内版本 |
| `keep-old` | 保留目标现有 Agent，跳过包内该 Agent 的全部资产，记入 `warnings` 后继续 |

> 字段级 merge（如 memory 记录按 id 去重合并）属 v2 增量导出/合并阶段（§9）范畴，v1 不实现——避免"半新半旧"的不可预期状态。

## 6. 敏感文件排除清单

以下文件**永不入包**（双保险层；白名单扫描根本身已排除绝大多数）：

| 路径模式 | 原因 |
|----------|------|
| `*.slime_pass*` | passphrase 文件 |
| `providers.enc.json` | 加密的 provider 配置（含 API 密钥） |
| `auth_token*` | 认证 token |
| `*.enc` | 所有加密配置文件 |
| `.obsidian/**`、`.trash/**` | Obsidian 应用自有目录（vault 设置/回收站，非 Agent 资产，见 §2.2） |
| `config/history.jsonl` | 对话历史（隐私 + 体积；路径核验自 `core-ts/src/services/history.ts`，v1 不迁移） |
| `config/skills/**` | 第三方技能库（非 Agent 资产，目标设备各自安装） |
| `data/{agent_id}/lancedb/**` | 向量索引（派生数据，导入后按 rebuild_hints 重建） |
| `data/generated/**` | 媒体生成产物（非永存资产） |
| `data/model_servers.json` | 模型注册表（设备本地运行时状态） |
| `data/mcp/**` | MCP 运行时缓存 |
| `data/loadtest/**`、`data/logs/**`、`data/spike/**` | 测试/日志产物 |
| `data/audit*.jsonl`、`data/qa_*` | 审计与 QA 日志 |

**规则**：排除清单由程序硬编码，不可通过 manifest 覆盖。

## 7. 兼容性规则

### 7.1 向前兼容（强制）

新版本必须能导入旧版本导出的包：

- `schema_version` 向后兼容：v1 的 schema_version 字符串不变，新字段可选
- `layout_version` 低于当前 → 按注册的 migration_hooks 逐级升级资产布局（如未来 agents.json 内嵌字段拆分为 `data/agents/{id}/` 独立目录）；等于当前 → 直接导入；**高于当前 → 明确报错**
- `export_version` MAJOR 不同 → 明确报错（不静默半导入）
- `export_version` MINOR/PATCH 不同 → 静默兼容，忽略未知字段
- 旧包缺 `rebuild_hints` 字段 → 按默认 `["lancedb"]` 处理（新版本必须能为旧包重建派生索引，见 §3.1）
- `migration_hooks`：新版本可添加钩子处理旧数据迁移

### 7.2 向后兼容（尽力）

旧版本遇新包时：

- `schema_version` 高于已知值 → 报错："需要升级 slime 版本"
- `export_version` MAJOR 高于已知值 → 报错："包格式不兼容，请升级"
- 不应静默跳过或不完整导入

### 7.3 迁移钩子（v2+ 规划）

```json
"migration_hooks": [
  {
    "from_version": "1.0.0",
    "to_version": "1.1.0",
    "description": "memory.json 新增 links 字段迁移",
    "script": "migrate_v1_to_v2.js"
  }
]
```

v1 规格中 `migration_hooks` 为空数组，v2 实现时填充。

## 8. API 设计

### 8.1 导出 API

```typescript
// core-ts/src/services/export.ts
interface ExportOptions {
  agentId: string;
  output: string;  // .slimeagent 文件路径
  excludeSensitive?: boolean;  // 默认 true
}

interface ExportResult {
  ok: boolean;
  path?: string;
  error?: string;
  manifest?: Manifest;
}

async function exportAgent(options: ExportOptions): Promise<ExportResult>;
```

### 8.2 导入 API

```typescript
interface ImportOptions {
  input: string;      // .slimeagent 文件路径
  targetRoot: string; // 目标永存资产根（解压目标 = config/ + Knowledge/；data/{id}/lancedb 按 rebuild_hints 重建而非解压）
  conflictStrategy: "abort" | "overwrite" | "keep-old";  // 默认 "abort"，语义见 §5.2
}

interface ImportResult {
  ok: boolean;
  agentId?: string;
  agentName?: string;
  error?: string;
  warnings?: string[];
}

async function importAgent(options: ImportOptions): Promise<ImportResult>;
```

### 8.3 验证 API

```typescript
/** 验证包完整性（不解压，仅检查 manifest + SHA-256） */
async function verifyAgentPack(path: string): Promise<{ ok: boolean; errors: string[] }>;
```

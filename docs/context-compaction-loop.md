# slime 上下文压缩 Agent-Loop（设计定稿 · A-1081）

> 依据：三份权威检索报告（一手来源见 §7）+ 本机实测证据（§1.2）。目标不是"加一个压缩按钮"，
> 而是把**压缩**变成 Agent-Loop 里一个**闭环、可验证、不可绕过的环节**。

---

## 1. 现状诊断（为什么"压缩并非真压缩"）

### 1.1 现在的环路只有两段，中间缺了三环

```
[阈值触发] → 摘要轮 → setSessionSummary() → 下一轮 loadSessionHistory() 注入「摘要头 + 最近 K 行」
                  ↑                                                                    │
                  └───────────── 没有任何校验：降了多少？还能用吗？真的更小了吗？──────────┘
```

缺的三环：
1. **校验环**：压缩后**没有验证**体积真的下降、消息序列仍然合法。
2. **理解环**：摘要生成后**没有回读**（没有"理解总结内容"这一步）——摘要写错了没人发现，
   下一轮模型拿着错的摘要继续做。
3. **反应环**：上游**已经报"太长"**时，循环里**没有人去压缩**，只有无脑重连。

### 1.2 本机实测证据（D:\pilot project）

| 位置 | 实测 | 问题 |
| --- | --- | --- |
| `context_compress.ts: estimateHistoryTokens` | `chars / 4` | **CJK 4 倍低估**（1 汉字 ≈ 1 token，却按 0.25 算）⇒ 该触发时不触发 |
| `context_compress.ts: buildCompactedHistory` | `[...tail.map(m => ({role, content}))]` | **丢弃 `tool_calls` / 工具结果**，并把 `tool` 角色塌成 `user` ⇒ 角色序列与工具配对都被破坏 |
| `context_compress.ts: hardTruncate` | `[首条, ...末 K]` | 中段**无摘要直接丢**；且首尾不相邻（对话不连续） |
| `main/index.ts: loadSessionHistory` | `loadHistoryForSession(..., 50, ...)` | 历史先被**静默截到 50 条**，超出部分既不进摘要也不出声 |
| `main/index.ts: slime:chat:compress` | `if (used > histUsed && history.length <= K+2) return skipped` | 固定开销（系统提示/记忆/技能/工具定义/工作区注入）占大头时**空转**——**每轮都判 skipped，什么都不会变** |
| `engine.summarizeContext` | `SUMMARIZE_INPUT_CAP = 9000` 超限即 `return null` | 放弃摘要 → 降级**硬裁剪**：回执写着"已压缩上下文"，实际**一个字都没总结** |
| `ChatPanel.maybeAutoCompress` | 压缩成功即 `ctxBaseRef = ctxAnchorRef = round(cap * 0.5)` | **假报**：把占用直接写成"上限的 50%"，与真实体积无关 ⇒ 界面（和后续判定）以为压下去了 |
| `ChatPanel` onError | `MAX_RETRY = 9`，`PERMANENT_STATUSES = [401,403,404]` | **400 不在终态**：上下文超限的 400 / 上游挂住导致的超时，都会被当成"可重试" ⇒ **9 次重连** ⇒ "连接半天还是重连" |

### 1.3 完整故障链（与用户症状一一对上）

```
长会话（历史 + 固定开销）逼近/超过该模型窗口
   → 上游返回 400(context_length_exceeded)  或  干脆挂住不出首字节
   → 客户端：400 不在终态名单 → 判"可重试"；挂住 → 空闲超时（也可重试）
   → 9 次重连（每次递增退避 + 60s 空闲超时）
   → 用户看到："连接半天还是重连" → 最终"直接超时报错"
   而同一模型在**新会话**里请求小得多 → 正常 ✓（"用不了的模型在其他会话还能用"）
   小红书 dot4 是 512K 窗口 → 同样的巨大请求它扛得住 ✓（"只有小红书的模型能稳定使用"）
```

**结论**：这不是"某个供应商坏了"，是**我们自己的请求没有被压缩住**，且**失败分类把超限当成了瞬时故障**。

| --- | --- | --- |

| **append-only / 带支撑重写 > 覆盖式重写** | 检索报告的结论（H1/H5/H7 证据线）：语义替换无单调性保证 | **递进式摘要**：新摘要必须包含旧摘要 + 新内容，且**旧摘要原文留档**可回滚 |
| **熔断**：连续压缩失败 3 次即停 | Claude Code auto-compact 行为 | 必须有**连续失败计数 + 上限**，否则"压缩→失败→再压缩"死循环 |
| **两段式**：先 tool-result clearing（成对、留占位），再 LLM 摘要 | Anthropic 工程博客（effective context engineering） | 消 P95 尖峰最快的一招，且**不破坏配对** |
| **裁剪只作用于本次输入**：本地全量保留 | Anthropic 工程博客 + 产品实践 | 压缩**不许**销毁本地历史（可回滚、可审计） |
| **摘要要短、关键信息置顶置尾**；聚焦式摘要 > 塞满 | "Lost in the Middle"、Chroma "Context Rot"（二手，报告中已标注） | 摘要模板要**分节 + 精简**，且**首尾放最关键的**（任务状态 / 下一步） |
| **分层超时**：connect / first-byte / idle / total | 报告③的工程结论 | 挂住不该等 60s×9 |

## 3. slime 专属压缩 Agent-Loop（状态机）

```
                    ┌──────────────────────────────────────────────────────┐
                    │  ① 观测（每轮 & 流式期间）                            │
                    │     used = 实测输入侧（prompt_tokens + cache_read）    │
                    │     与「按真实文本重估的估算」取 max，杜绝 4 倍低估     │
                    └───────────────┬──────────────────────────────────────┘
                                    │ used ≥ cap × ratio ?
                    ┌───────────────▼──────────────────────────────────────┐
                    │  ② 决策：选一档动作（唯一出处 planCompaction）         │
                    │     none      ：什么都不做（并**如实说明为什么**）      │
                    │     clear     ：只清工具结果（成对 + 占位）            │
                    │     summarize ：清工具结果 + 摘要（首选）              │
                    │     trim      ：turn 对齐裁剪（摘要不可用时）          │
                    └───────────────┬──────────────────────────────────────┘
                                    ▼
                    ┌──────────────────────────────────────────────────────┐
                    │  ③ 实施（在**本次请求的副本**上，不动本地历史）        │
                    │     · 切口按**整轮**对齐（start_on=user）              │
                    │     · tool 配对完整性校验（成对、顺序、数量）           │
                    └───────────────┬──────────────────────────────────────┘
                                    ▼
                    ┌──────────────────────────────────────────────────────┐
                    │  ④ 总结（摘要轮，输入有硬上限；超限先 clear 再摘要）    │
                    │     递进式：newSummary = f(priorSummary, 新增轮次)      │
                    └───────────────┬──────────────────────────────────────┘
                                    ▼
                    ┌──────────────────────────────────────────────────────┐
                    │  ⑤ **理解**（用户明确要求的那一环，A-1081 新增）        │
                    │     让模型回读摘要并**自述当前状态**：                  │
                    │     任务目标 / 已完成与证据 / 未决 / 下一步 / 约束      │
                    │     ⇒ 产出「续接锚」；**理解失败 ⇒ 视为压缩失败**        │
                    └───────────────┬──────────────────────────────────────┘
                                    ▼
                    ┌──────────────────────────────────────────────────────┐
                    │  ⑥ 校验（硬不变量，任何一条不过 ⇒ 回滚 + 计数+1）      │
                    │     · 体积真的下降（≥ 阈值降幅）                        │
                    │     · 角色交替合法、以 user 开场                        │
                    │     · 工具配对完整（数量/顺序）                         │
                    │     · 摘要在场且非空                                    │
                    └───────────────┬──────────────────────────────────────┘
                                    ▼
                    ┌──────────────────────────────────────────────────────┐
                    │  ⑦ 继续（用压缩后的输入发本次请求）                     │
                    │     实测落回 → 更新锚点（**只信实测**，不假报）          │
                    └───────────────┬──────────────────────────────────────┘
                                    │ 再次达阈值 ⇒ 回到 ①（多环）
                                    ▼
                    ┌──────────────────────────────────────────────────────┐
                    │  ⑧ 熔断（连续失败 ≥ 3 ⇒ 停止压缩，如实告知 + 给可操作项）│
                    └──────────────────────────────────────────────────────┘

  反应式入口（与阈值触发并列，二者**汇入同一个状态机**）：
    上游返回"上下文/请求过长"类错误  ⇒  标为**终态（不重连）** + 触发一次 ②→⑦
    ⇒ 这才是"少了一环"的那一环：**上游说太长 → 我们压缩 → 再试一次**，而不是原地重连 9 次
```

### 3.1 硬不变量（每次压缩都必须成立，写成守卫）

| # | 不变量 | 为什么 |
| --- | --- | --- |
| I1 | `tool_calls` 数量 == 紧随其后的 `tool` 结果数量，且顺序一致 | 缺一个就 400（且常在下一次请求才炸） |
| I2 | 裁剪切口落在**整轮边界**（以 `user` 开场；不以孤立 `assistant.tool_calls` 结尾） | 半轮 = 配对被切断 |
| I3 | 压缩后序列**以 user 开场**、无连续同角色 | Anthropic 系硬要求 |
| I4 | 压缩后估算体积 **< 压缩前 × (1 - 最小降幅)** | 否则叫"假压缩"（当前假报 cap×0.5 的病根） |
| I5 | 摘要非空、且**包含** priorSummary 的全部要点（递进式，不允许倒退） | 防止信息逐轮衰减 |
| I6 | 本地全量历史**零改动**（压缩只作用于本次输入副本） | 可回滚、可审计 |
| I7 | 连续失败 ≥ 3 ⇒ 停（不做第 4 次） | 防压缩死循环 |

### 3.2 触发判据（唯一出处 `planCompaction`，纯函数）

输入：`{ used, cap, ratio, turns, toolResultTokens, lastFailure, priorSummary }`
输出：`{ action: none|clear|summarize|trim, cutAt, reason }`

- `used < cap × ratio` → `none`
- 且 `toolResultTokens / used ≥ 0.3`（工具结果占大头）→ `clear`（先摘低垂果实）
- 否则 → `summarize`
- 摘要不可用（无模型/输入超限/熔断中）→ `trim`
- **任何"什么都不做"的分支都必须带 `reason`**，并**如实显示给用户**
  （现状的 `skipped` 是静默的 —— 用户看到"逼近阈值却毫无动作"）

## 4. 关键设计决策（含"明确不做"）

1. **不换原始对话**：本地历史永远全量保留；压缩结果只进"本次请求的输入副本"（I6）。
2. **不做 token 级/注意力级压缩**：LLMLingua/Gist/KV-cache 类方案要么需重训、要么改推理内核，
   与本产品"多供应商 HTTP 客户端"的形态不符（且会**摧毁工具调用结构**）。
3. **摘要是"可回滚工件"**：每次压缩落一份带时间戳的摘要存档，用户可看、可回滚。
4. **"理解"环不可省**：它同时充当**摘要质量的自检**（理解不出下一步 ⇒ 摘要不合格 ⇒ 重做/降级）。
5. **反应式与阈值式共用同一个状态机**，不写第二条路径（否则必然漂移）。
6. **假报是 bug**：界面上的占用**只能**来自实测（`prompt_tokens` / 真实文本重估）。

## 8. 定稿补充：第二轮权威报告里**改变设计**的硬证据

这几条不是"补充参考"，而是**推翻了朴素做法**的实证，必须写进实现：

### 8.1 顺序不可换：offload → notify → 掩码 → 摘要 → trim

JetBrains 2025-06 实测（NeurIPS 论文 / 工程博客）：**把旧消息掩码掉**而非摘要掉，
把长上下文任务质量**打平到摘要水平**、成本便宜 15 倍、首字节快 13–18%。
⇒ slime 的动作顺序固定为 **① 工具结果清理（成对 + 占位）→ ② 摘要 → ③ turn 对齐裁剪**。
**反过来（先摘要）会先把可廉价清理的部分烧进摘要里，永久损失。**

### 8.2 摘要必须用**被动语态**，且**禁止指令式字段**

Anthropic 官方 template 的字段名本身就是设计：
`AskQuestion`（"the user asks…"）、`NextStep`（"pending tasks"）、
`CurrentWork`（"the only allowed next action is … if appropriate"）。
原因（官方实测）：摘要里出现**命令式**句子（"接下来只允许调用 X"）会被下游模型当成**用户指令**，
污染下一步决策。⇒ 压缩 prompt 的模板要**照抄这套语义**，并在守卫里锁"不许出现第二人称命令句"。

### 8.3 子代理边界必须先做**边界重置**再压缩

Anthropic 实证事故：在 subagent 轨迹里 `tool_choice` 泄漏，导致**API key 被送到错误的服务**。
⇒ 主+子轨迹拼接成一条长串再摘要 = 把跨代理污染固化进摘要。
**判据：压缩前必须先在子代理边界重映射/重置（谁在说话、允许做什么），不许直接摘要拼接串。**

### 8.4 异步压缩必须有 **generation / skip-stale**

OpenAI Agents SDK 的 `Session` 已内建：压缩**在后台异步发生**，但请求随时可能发出
⇒ 必须防止"新压缩结果被一个更早的请求套用"。
⇒ slime 的 `setSessionSummary` 要带 **generation 号**；请求侧只接受
`generation >= 自己出发时看到的那个`，过期摘要直接丢弃（并把那次压缩标为 stale）。

### 8.5 压缩后要**暂停一轮**：AWAIT_COMPREHEND

新出现的实践（本轮报告里为"次新"档，需标注）：压缩后 `pause_after_compaction`，
注入"任务规格 + 用户约束 + 边界"，**等模型产出「续接认知」再放行**。
⇒ 这正好是你要的"**理解总结**"那一环的工程形态：它是**一个独立的、可失败的状态**
（失败重试 2 次后**非阻塞降级**并留痕），不是随手加一句 prompt。

### 8.6 两个**防抖**数字（照抄业界实测值）

- **50% 资格闸门**：`tokensBefore > 50% × window` 才允许压缩（Claude Code 实测防 compaction thrashing）。
- **熔断 3 次**：连续 3 次压缩失败即停（Claude Code 同款）；
  但失败计数要记在"**同一段历史是否已被掩码处理过**"这个维度上 ——
  JetBrains 实证的坑正是"坏历史没被救出来，却每轮都在重送"。

### 8.7 「理解」环必须**有界**

ReSum 的教训（阿里通义）：给模型无限推理空间去"理解"是不可接受的生产成本。
⇒ slime 的理解环固定为：**一次调用、固定输出 schema（5 个字段）、有硬超时**，不许多轮自省。

### 8.8 把"没裁下来"作为**一等状态**如实说出

现场实测最常见的失败是**裁完还是超限**（Replit/OpenAI 论坛一手）：
压缩前 82k → 压缩后 63k → 仍然超 32k 窗口。
⇒ 压缩结果必须回带 `tokensBefore / tokensAfter / dropped / stillOverflow`，
**超限就明说"压缩后仍超限，需要换模型或开新会话"**，不许静默。
（这正是本仓 `ctxAnchorRef = cap × 0.5` 那个**假报**要改成的形态。）

## 9. 已落地补充（A-1083）：**发送前预算门** —— 把「发出去才知道超」翻成「发之前就知道」

设计定稿 §3 的环路里，第 ① 步「观测」原本只回答"现在占多少"；**它缺一半**：
还得回答"**这一发会不会超**"。事故的根正在这里 —— 长会话发出去 → 上游 400(超长) 或挂住不出首字节
→ 被当"可重试" → 每轮最长 300s × 最多 10 次 ⇒ 「连接半天还是重连」。

**唯一出处**：`core-ts/src/services/context_loop.ts` 的 `planSend()`（穷举可测）。

| 顺序 | 条件 | 动作 |
| --- | --- | --- |
| 1 | `cap ≤ 0`（窗口未知） | `ok` —— **不猜、不拦**（猜错会把能用的模型也拦掉） |
| 2 | 三档触发任一成立（上游报超限 / 预算不足 / 用户阈值） | 需要压缩 |
| 3 | 需要压缩且**有**可压素材 | `compact` —— **先压再发** |

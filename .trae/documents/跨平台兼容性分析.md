# Slime 跨平台兼容性分析与移动端可行性报告

## 目标
1. 输出 Linux/macOS 兼容性现状报告（只读，不修改代码）
2. 输出移动端的可行性调研（不实现，只做技术选型分析）

---

## 一、Linux 兼容性现状

### ✅ 已支持（无需修改即可运行）

| 组件 | 状态 | 说明 |
|------|------|------|
| Python 后端 (slime_server/cli) | ✅ | 使用 `pathlib.Path`，跨平台路径处理正确 |
| TypeScript 核心 (core-ts) | ✅ | 纯 Node.js，无平台绑定 |
| MCP 协议 | ✅ | stdio/HTTP 双传输，跨平台 |
| 记忆/检索/工具轮/沙箱/Swarm | ✅ | 纯业务逻辑，无平台依赖 |
| LanceDB 向量存储 | ✅ | 有 Linux x64 预编译二进制 |
| encryption.ts 权限保护 | ✅ | Linux 走 `chmod(0o600)`，Windows 走 `icacls` |
| electron-updater | ✅ | 支持 Linux AppImage/Deb/RPM |
| sidecar (FastAPI) | ✅ | 跨平台 Python 服务 |

### ⚠️ 部分支持（运行时可用，打包需配置）

| 问题 | 位置 | 影响 | 修复难度 |
|------|------|------|----------|
| **孤儿检测缺失** | `model_server.ts:286` `parentPid()` 非 Windows 返回 null | Linux 上崩溃的 llama-server 不会被自动回收，需手动 kill | 低 — 用 `/proc/{pid}/status` 或 `ps --ppid` 替换 wmic |
| **VRAM 监控** | `model_server.ts:50` `nvidia-smi` | 无 NVIDIA GPU 时返回 null 被跳过（已处理），AMD/Intel GPU 无法检测 | 中 — 可加 ROCm 回退，或保持当前行为 |
| **slime.toml 默认路径** | `slime.toml:101,107,115,162,171` | 新安装用户在 Linux 上需手动修改所有路径 | 低 — 模板改用相对路径或 `{HOME}` 占位符 |
| **Electron 打包配置** | `gui/electron-builder.json` | 只有 `win` 目标，无 `linux`/`mac` | 低 — 加配置即可 |

### ❌ 阻断 Linux 打包的问题

| 问题 | 说明 |
|------|------|
| **LanceDB 原生模块** | 当前只有 `lancedb.win32-x64-msvc-*.node`，Linux 需要 `lancedb.linux-x64-gnu.node` |
| **打包脚本** | `dist:win` 硬编码 `--win`，无 `dist:linux` 脚本 |

## 二、macOS 兼容性现状

与 Linux 相同的基础问题，额外注意：

| 问题 | 说明 |
|------|------|
| **Gatekeeper 签名** | macOS 需要代码签名才能运行，electron-builder 支持但需配置 `mac` 字段 |
| **Notarization** | 分发需 Apple notarization（可选但推荐） |
| **Apple Silicon (ARM64)** | LanceDB/onnxruntime 需有 arm64 二进制 |

## 三、移动端可行性调研

### 当前架构与移动的冲突

| 冲突点 | 详细说明 |
|--------|----------|
| **Electron = 桌面框架** | 无法在 iOS/Android 运行 |
| **本地进程管理** | llama-server spawn/kill 依赖完整 OS 进程控制，移动端沙箱不允许 |
| **GPU/VRAM 假设** | `nvidia-smi`、显存监控在手机上不适用 |
| **文件系统权限** | 移动端文件访问受限，安全文件处理方式不同 |
| **网络架构** | sidecar 绑定 localhost，移动端需远程 API 模式 |

### 可行方案对比

| 方案 | 优点 | 缺点 | 工作量 | 推荐度 |
|------|------|------|--------|--------|
| **React Native + 远程 API** | 复用现有 FastAPI，移动端只做 UI | 本地模型无法运行，需云端推理 | 中（2-3 周） | ⭐⭐⭐ |
| **Tauri (iOS/Android)** | 更轻量，Rust 后端性能好 | 移动端支持尚不成熟，社区小 | 高（1-2 月） | ⭐⭐ |
| **PWA (Progressive Web App)** | 零安装，跨平台，开发快 | 无本地存储/进程管理，功能受限 | 低（1 周） | ⭐⭐⭐⭐ |
| **Flutter + REST API** | 性能好，原生体验 | 需全新开发 UI | 高（1-2 月） | ⭐⭐ |

### 推荐路径

**短期（1-2 周）**：
- 先做 PWA 原型，验证核心对话流程在浏览器可用
- 复用现有 FastAPI 后端，无需改动

**中期（1-2 月）**：
- 如果 PWA 验证通过，考虑 React Native 原生应用
- 重点解决：离线模式（本地 SQLite 缓存）、推送通知、生物识别登录

**长期（3+ 月）**：
- 评估是否需要本地模型推理（移动端 NPU 支持）
- 考虑 Tauri 或原生开发

## 四、结论与建议

### 桌面端（Linux/macOS）
- **当前状态**：运行时基本可用，打包需少量配置
- **建议**：暂不修复（按用户要求只出报告），后续如有需求再修
- **预计修复时间**：2-4 小时

### 移动端
- **当前状态**：完全不支持，需全新架构
- **建议**：先做 PWA 原型验证可行性，再决定是否需要原生应用
- **预计探索时间**：1-2 周（PWA 原型）

### 优先级排序
1. **PWA 原型**（验证移动端可行性，1 周）
2. **Linux 打包修复**（按需，2-3 小时）
3. **React Native 原生应用**（如 PWA 验证通过，2-3 周）
